### 1.3 触发面（gate 条件）与我方同配置行为——实操风险定级

真值 `requiresClientRequestSigning`（@3712130）：
1. 免签：zhipu-account start-plan / off-peak（仅记 access_mode 日志）。
2. 强制候选：zhipu-coding-plan-api-key；zhipu-account individual/team；或 baseURL 主机 ∈ z.ai/bigmodel.cn 族（含子域）或 ∈ {api.chatglm.site, zcode.chatglm.site}。
3. 候选 ≠ 必签：仍需 gate（/api/v1/agent/configs 的 codingPlanSignature.enable）开启才实际签名；gate 不可达/关闭/fail-open 时真值也走 unsigned。

我方在同样配置下的行为（逐面）：
- **builtin individual/team（zhipu-account）**：我方把官方端点重写为平台网关（K10，official-coding-plan-gateway.ts:22-31 + model-execution.ts:516-521），带 `Authorization: Bearer <coding-plan api key>` 发网关，**无签名**。真值则签名后**直连官方端点**。⇒ 官方套餐主链路是否被拒取决于**网关**是否强制 V4：若网关不查七头则我方现行可用（K10 掩蔽生效）；若网关对 /api/v1/ultra* 路径也校验客户端签名，则我方官方套餐请求全量失败。此为运行时问题（沿用 pass27 Q1），静态无法定谳；但注意我方 model-execution.ts:450 注释已记录服务端存在 "zcode-plan 安全校验拒绝（3007）" 先例，说明同族端点有服务端校验传统。
- **zhipu-coding-plan-api-key（手工 key 直连官方端点）**：命中我方网关改写的仅两条精确 URL（open.bigmodel.cn / api.z.ai 的 /api/anthropic/v1/messages）；其余路径（如非 /v1/messages 或带查询变体不匹配时）直连官方端点且**无签名**——若服务端 gate 开启，预期被 401/300x 类拒绝（我方 createProviderBusinessErrorFetch 会转成 ProviderBusinessError，用户可见失败而非静默成功）。
- **自定义 api-key provider 指向 z.ai/bigmodel.cn/chatglm.site 族主机**：真值会签名，我方恒 unsigned 直连。这是 K1 最干净的暴露面：一旦这些域的服务端启用校验，我方这类配置全部失败。
- **结论**：gate 未开启时两侧同为 unsigned、无现行行为差（K1 维持"定时炸弹"定性）；起爆条件 = 服务端对上述任一面开启 codingPlanSignature。我方唯一掩蔽层是 K10 网关路由，其是否兼容签名校验不可静态判定。维持 P1（主链路功能缺失，触发即恒败）。
