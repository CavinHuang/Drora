### 官方 win 两分支各传哪些字段

win32 entry 侧 `runWindowsDevHelper`（34167）把 `runHelper` 作为 `options.startBroker` 默认值（34178）。两分支调用：

**延迟分支（`deferNativeInitialization === true`，34190-34218）**——`startBroker({...})` 只传 6 个字段（34193-34218）：
- `native: deferredNative.surface`（34194）
- `system: deferredSystem.surface`（34195）
- `socketPath: config2.socketPath`（34196）
- `deferBackendInitialization: true`（34197）
- `onTransportReady: async ({ socketPath }) => {...}`（34198-34214）
- `onReady: ({ socketPath }) => { boundSocketPath = socketPath; }`（34215-34217）

**立即分支（else，34219-34234）**——只传 4 个字段（34226-34233）：
- `native`（真 addon，34220 加载）、`system`（34223）、`socketPath`（34229）、`onReady`（34230-34232）。**不传** `deferBackendInitialization`（缺省即 false，33625 严格 `=== true`）。

两分支都**不传**：`verifyPeer`、`peerIdentityAuth`、`version`、`brokerInfo`、`logger`、`idleExit`、`startupAllowed`、`admitControllerAction` 等全部可选面。

分支选择逻辑 34180：`const deferNativeInitialization = options.deferNativeInitialization ?? options.startBroker === void 0;`——生产路径（未注入 startBroker）恒为延迟分支。

### deferBackendInitialization / onTransportReady 语义

`runHelper` 内部顺序（33789-33854）：
1. `if (!deferBackendInitialization) { initializeBackend(); }`（33789-33791）——立即分支在构造 server 前就建 backend。
2. `const deferredBackend = deferBackendInitialization ? createDeferredBackend(brokerInfo) : null;`（33792）。`createDeferredBackend`（**33584-33612**）：Proxy backend，未 setTarget 前除 `broker_info`（返回 brokerInfo，33593）外任何方法抛 `BrokerError("broker_unavailable", "Windows CUA broker backend is warming up", { ready_state: "warming_up", request_delivery_state: "not_sent" })`（33594-33600）。
3. `const server = new CuaPermissionBrokerServer({ socketPath: options.socketPath, backend: deferredBackend?.backend ?? activeBackend, ... })`（33814-33843）。
4. `await server.start();`（33844）。
5. `await options.onTransportReady?.({ socketPath: options.socketPath });`（**33846**）——**在 server.listen 成功之后、真实 backend 初始化之前**调用。
6. `if (deferBackendInitialization) { const initializedBackend = initializeBackend(); deferredBackend.setTarget(initializedBackend); }`（33847-33850）——onTransportReady 成功返回后才建真 backend 并接管。
7. onTransportReady 抛错则 `await server.stopEventually().catch(() => void 0); throw error62;`（33851-33854）——先停 server 再向上抛。

entry 侧 `onTransportReady`（34198-34214）内部顺序：
1. `const sent = await sendControl(runtime, { protocol: WINDOWS_DEV_CONTROL_PROTOCOL, type: "transport_ready", socketPath, pid: runtime.pid });`（34199-34204）。
2. `if (!sent) throw new Error("transport-ready IPC channel closed");`（**34205**）——sendControl 的语义（34115-34139）：有 `runtime.send`（IPC channel）时 `send(message, callback)`，callback 收 error 或 try/catch 抛错都 resolve(false)；无 send 时退化写 stdout JSON 行。**抛错条件即 transport_ready 控制消息投递失败（IPC 通道已关或 send 抛错）**。
3. 加载真 addon：`const native = loadNativeAddon({ platform: "win32" });`（34206）。
4. 鉴权门：`assertPeerIdentityAuthCapable(native, allowUnauthenticatedLocalDev);`（34207，见 C）。
5. ghost 开关：`enableGhostCursorOnNative(native, config2);`（34208，见 D）。
6. 建 system surface：`createSystemSurface({ platform: "win32" })`（34209-34211）。
7. 接管 deferred surface：`deferredNative.setTarget(native); deferredSystem.setTarget(system);`（34212-34213）。
