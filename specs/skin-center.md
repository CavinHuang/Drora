# Skin center

## Scope and ownership

Drora offers a device-local skin preference in Appearance. The existing theme choice remains the sole owner of light, dark and system mode. A skin adds a palette preset, an optional custom accent color, an optional user image, image positioning, separate workspace panel background opacities and an optional image-color panel tint. It does not alter task, workspace or Agent state.

The UI store owns the accepted skin preference. Desktop uses its existing app-local Host broadcast to synchronize windows. Web uses same-origin `storage` events to synchronize tabs in one browser profile; it must never send skin metadata through the HTTP server's shared BroadcastService, which serves multiple devices. Local storage holds only the small, versioned preference. A separate local image store holds one imported raster image per browser profile. No image bytes enter broadcasts, AppSettings, workspace settings, logs or remote sessions. A remote workspace displays the local device's skin.

## Product rules

- Presets: Default, Ocean, Forest, Plum, Ink, Geometry and Celestial. Default preserves the current visual design. Ocean, Forest and Plum use atmospheric landscape art; Ink uses restrained brushwork on paper, Geometry uses a modernist arrangement of shapes, and Celestial uses a quiet night sky. Each non-default preset includes a bundled, optimized raster wallpaper and matching accent colors. These assets ship through the Desktop and Web static asset pipeline; selecting a preset never uses the remote workspace asset service or persists image bytes. The same artwork receives a light or dark CSS tint so it remains quiet beneath workspace panels. A missing bundled asset falls back to the preset gradient. The user may choose one custom `#RRGGBB` accent; the rendered brand color is adjusted toward black or white only as far as needed for readable contrast in each light/dark mode. Custom color overrides preset accent tokens but keeps the chosen preset background. Clearing the custom color restores preset colors. Theme mode still controls light/dark semantic foundations and native title bar.
- Built-in image files and their generation prompts live in `packages/ui/src/skin/wallpapers/`. They are package assets, not accepted user skin state; adding art does not change the preference schema or broadcast payload.
- The user may import PNG, JPEG or WebP up to 8 MiB. Identify the format from its byte signature and confirm the browser can decode it with nonzero dimensions before saving; file extension and browser-reported MIME are advisory because desktop file pickers may omit or misreport them. An image import commits the preference only after bytes are saved. Invalid or failed imports keep the previous skin.
- The chosen image is local to this device/browser profile and takes priority over bundled preset art. Clearing it restores the preset background. If its stored bytes are unavailable on restore, render the preset background and keep controls usable.
- Image fit is cover. Position is a percentage pair and starts at center. Conversation, sidebar and side pane shell backgrounds each have an independent opacity slider, 20–100%, default 100%. Lower values reveal more of the wallpaper and can reduce the legibility of unboxed text on a busy user image; the controls explain this tradeoff. Text, borders, cards, overlays, browser guest content and terminal canvas never inherit panel opacity. The terminal frame and xterm canvas remain opaque.
- With a wallpaper visible behind a low-opacity draft home, the empty conversation region uses a soft, localized theme-colored focus veil behind the greeting and composer instead of frosting the entire wallpaper. The large outline watermark is hidden where it would compete with the artwork. The sidebar adds a slight theme-colored reading veil and strengthens its faint metadata. These projections do not change the accepted opacity values, task history, editor cards, dialogs or settings preview. With the default skin and no wallpaper, the original draft home remains unchanged.
- The user may independently enable image-color panel tinting. It is off for existing and fresh profiles so upgrading does not change accepted colors. When enabled, the three workspace panel shell backgrounds use a recognizable but restrained tint based on the active wallpaper's representative color while retaining distinct light/dark theme brightness and each panel's opacity. Changing between differently colored presets must visibly change the tint in both Zai themes, including at 100% panel opacity. Built-in presets use stable colors curated from their artwork. A custom imported image takes priority: its local bytes are downsampled once per image revision and a representative color is derived without sending or persisting image bytes or palette metadata. Monochrome images use a neutral tint instead of borrowing the selected preset's hue. Image-color tinting does not use the custom accent color and does not recolor text, cards, settings, browser guests or terminal canvases. Without an image, the ordinary theme surfaces remain. A missing custom image or extraction failure falls back to the preset tint or ordinary theme surfaces.
- The wallpaper is painted as the workspace shell background, beneath workspace panels. It must not depend on a negative stacking level, which can place the artwork behind the opaque window frame. Its selector must identify the workspace shell; the shared `DesktopWindowFrame` is also used by Settings and error views. It does not appear in settings (outside the intentional preview), share pages, onboarding or the operating system desktop. The opacity controls explain that lowering panel opacity reveals more of the wallpaper.
- Applying a preset or changing opacity is immediate. Reset returns to Default with 100% panel opacity and no image; it does not change light/dark theme mode.
- System theme changes keep the selected skin while reevaluating its light/dark palette.
- Windows, macOS and Linux retain their existing window frame and native title bar behavior. Mobile Web uses the same preference but may show an opaque panel for readability.

## Event order

```text
user action → validate preference or decode image → write image bytes if changed
            → UI store commit → persist versioned metadata → apply CSS projection
                              → Desktop Host broadcast OR Web same-origin storage event
                              → other local windows reread image, if revision changed
```

The UI store is the only owner of accepted skin metadata, including the image-color tint switch. The derived representative color is a disposable CSS projection, never a second accepted preference. Preview controls may hold local draft values, but do not create a second persisted truth. Image load and color extraction use the same monotonically increasing request generation: a late read or sample cannot replace a more recent skin. Removing an image revokes its object URL and clears its derived color. Desktop broadcast receivers validate metadata before applying it and do not rebroadcast. Web storage receivers apply the already-persisted metadata without writing it again.

## Failure semantics and migration

A missing or malformed preference falls back to Default. Unknown preset IDs, malformed custom colors and out-of-range opacity/position values normalize to supported values. Existing `drora-theme` values are unchanged. Version 2 metadata uses `drora-skin-v2`; older version 2 values without the image-color switch normalize it to off. When version 2 is absent, version 1 metadata migrates its single `panelOpacity` into all three panel opacities, keeping preset, image revision and position. A failed image import preserves the previous accepted preference. Clear/reset always removes the accepted image revision and applies the requested preference even if IndexedDB deletion fails; the UI reports cleanup failure and a later reset may retry file cleanup. Image bytes are not copied to or fetched from a remote Host.

## Acceptance scenarios

1. Fresh profile: original theme appearance, no image, opacity 100%.
2. Select each preset and a custom accent under Zai Light, Zai Dark and System; semantic text and status colors remain legible. Clearing the custom accent restores preset colors.
3. Import valid image, restart app and open another Desktop window: same background and settings are restored.
4. Invalid, oversized or undecodable image: clear error, no preference change.
5. Rapidly select two images: only the final selection is visible after asynchronous reads finish.
6. Move each opacity slider: only its workspace panel background changes; text/buttons/terminal canvas and settings page do not fade.
7. Clear image and reset skin: preset background and defaults return; light/dark mode is retained.
8. Open a remote workspace and mobile Web: no remote asset request; local fallback works when image bytes are missing. Two browser profiles connected to one Web server keep independent skins; two tabs in one profile synchronize.
9. Windows, macOS and Linux desktop frames retain radius, drag regions and title bar behavior.
10. A version 1 saved skin migrates to version 2 without losing the selected preset, image or opacity. Reset succeeds if image storage is unavailable and can later retry file cleanup.
11. Ocean, Forest, Plum, Ink, Geometry and Celestial display their bundled art in the workspace and matching thumbnails in Appearance on Desktop and Web, under both light and dark themes. Default remains unchanged; imported art takes priority and clearing it reveals the selected preset. Built assets resolve through the app's static asset pipeline without remote workspace asset service calls or IndexedDB reads.
12. Existing version 2 preferences continue to resolve to the same preset after the three new IDs are added; switching among all presets changes only the selected preset and keeps the user's custom image, accent and panel opacity choices.
13. At 95% conversation and sidebar background opacity, the workspace shell wallpaper still paints beneath both panels (though faintly). The Settings page stays opaque. The controls explain the relation between opacity and visible wallpaper.
14. Each panel slider reaches 20% and persists independently across restart and local-window synchronization; existing 80–100% values remain unchanged. Reset returns all three to 100%.
15. With image-color tint off, all panel colors match the previous theme rendering. Enable it on each preset under light and dark themes: conversation, sidebar and side pane use muted artwork hues at 20%, 95% and 100% opacity without recoloring text, cards, terminal or browser content. Default without an image remains neutral.
16. Import a saturated or multicolor image while tinting is enabled: the custom image supplies the tint, remains local, and does not change the custom accent. Clear it to restore the preset tint. Rapid imports, theme changes and opacity changes cannot apply a stale sampled color. Missing bytes or canvas sampling failure leave controls usable and use the preset or theme color.
17. Under Zai Dark and Zai Light, select Ocean then Forest with image-color tint enabled and all panel opacities at 100%: preview and workspace conversation/sidebar/right pane backgrounds change visibly, while text contrast remains readable.
18. Import a valid PNG, JPEG or WebP whose picker reports an empty or incorrect MIME and whose dimensions exceed 8192 pixels but whose file size is at most 8 MiB: signature and successful decode permit it. Unsupported bytes, zero-size and undecodable data are rejected without changing the selected skin.
19. Under Zai Dark and Zai Light at conversation/sidebar opacity near 35%, a draft home with a wallpaper keeps the image recognizable around the edges while greeting, composer and sidebar metadata remain legible. The oversized outline watermark does not overlap the artwork. Opening an existing task removes the draft focus veil; Default without wallpaper preserves its normal home.
